更新时间：2026-07-28

## 0. 本次修订结论

原路线的工程基础是正确的：可靠摄取、结构化来源、混合检索、权限过滤和离线评测，确实比“上传文档后调用大模型”更有含金量。

主要问题不在技术栈，而在产品边界：员工手册、信息安全、报销、采购、客服 SOP 同时展开，像一套通用 RAG 平台的功能清单，难以在几分钟内说明“谁在什么场景下为什么一定需要它”。在每天约 4 小时、面向秋招的约束下，这也会增加造数据、评测和演示成本。

本次将项目收敛为：

> 面向企业员工和财务审核人员的“差旅报销制度合规助手”，根据费用发生日期、差旅场景、制度版本和用户权限，给出可追溯的办理结论、材料清单与制度依据；证据不足时拒绝下结论。

这不是财务审批系统，也不替代财务人员作最终合规判断。它解决的是提交报销前的“找规定、辨版本、备材料”和审核过程中的重复制度咨询。

### 对原路线的调整

| 决策 | 内容 | 原因 |
| --- | --- | --- |
| 保留为核心 | 结构化解析、页码/章节引用、混合检索、可靠拒答 | 直接决定回答是否可验证 |
| 新增为核心 | 图片/扫描页检测、提取完整性警告和安全降级 | 带图片不等于需要多模态，但系统不能静默忽略未提取页面后仍假装制度完整 |

| 提前并贯穿 | 评测规格、领域题集、检索/回答/工具/端到端指标 | 评测不能在最后补；从 Stage 8 建集，后续每阶段都用同一套契约回归 |
| 新增为核心 | Prompt 版本管理、零样本基线、少样本对照与回归评测 | 提示词优化必须由冻结测试集证明，不能靠主观挑选示例或只展示最好的一次结果 |
| 提升为核心 | Function Calling、意图路由、只读报销状态查询、报销合规预检查 | 工具注册本身不是亮点，RAG 与结构化业务数据形成可评测闭环才有面试价值 |
| 加入主线但限制边界 | LangChain | 用于 Prompt、模型、结构化输出和工具绑定的适配编排；检索、权限和业务规则保持普通 Python 服务，避免框架锁定 |
| 加入辅助评测 | RAGAS | 补充上下文与回答质量评测并匹配岗位关键词，但不替代版本、引用、拒答、工具路由和越权等领域硬指标 |
| 后置到单一工作流 | LangGraph | 只编排报销合规预检查的多步骤、条件分支和失败路径；普通制度问答与状态查询不做成图 |
| 保留最小闭环 | JWT 身份、资源归属校验、只读工具、参数 schema、审计与攻击回归 | 不建设大厂级安全平台，但数据库工具上线前必须保证不会越权或执行任意 SQL |
| 保留但后移 | Redis + Celery、React、CI | 有工程价值，但不能先于可评测的 RAG 与工具调用闭环 |
| 降为对照实验 | reranker、流式回答 | 只有基线数据证明有收益才加入 |
| 降为可选适配 | MCP Server | 只在核心工具稳定、主演示与评测完成后，把一个现有只读工具包装成薄适配层；不为 MCP 反向扩张业务范围 |
| 本周期不做 | 完整多模态 RAG、发票/截图 OCR 与验真、MinIO/S3 实现、多 Agent、自动工作流审批 | 投入大且会把制度助手扩张成另一个发票审核项目 |
| 后置为条件增强 | 扫描版 PDF OCR | Stage 8 先识别并暴露 `needs_ocr`；只有代表性制度确实依赖扫描页且主线稳定时，Stage 16 才做限时 OCR 试点 |
| 缩小范围 | PDF/DOCX 是主要业务格式；Markdown/TXT 只保证基础支持 | 避免在低价值格式上平均用力 |

2026-07-27 路线复审结论：采纳“提高 Function Calling 与评测优先级”的方向，但不把未经统计口径支持的“市场覆盖率高”当作路线依据。Function Calling 已是 Agent 项目的常见基础能力，单独注册一个函数不足以形成差异化；本项目用“制度问答 → 状态查询 → 报销合规预检查”闭环证明工具选择、结构化数据访问和 RAG 证据组合能力。Prompt 优化、LangChain 和 RAGAS 纳入主线，分别形成版本化实验、有限框架集成和辅助评测证据；LangGraph 只服务于确有状态与分支的合规预检查，不重写整个 RAG。安全缩减为与权限和只读工具直接相关的最小闭环，不建设大厂级平台；MCP 保持可选，因为协议包装不能替代业务价值与评测结果。

2026-07-28 图片输入复审结论：本项目支持“包含图片的 PDF/DOCX 文件上传”，但 P0 只检索可可靠提取的文字，并检测图片页、扫描页和提取不完整情况；纯扫描文档无可用文字时安全失败，混合文档可进入 `ready` 但必须携带警告，未提取页面不得生成 chunk 或引用。JPG/PNG、发票照片、截图问答和图片向量检索不进入主线；扫描 PDF OCR 仅作为 Stage 16 的条件增强，因此本项目不宣称多模态 RAG。

补充报告基于 21 个 Agent 岗位，其中中国 14 个、海外 7 个；其公开口径是 `Function Calling / Tool Use / MCP` 合并统计为 18/21，`Eval / 可观测性` 为 14/21，`安全 / 合规 / 治理` 为 10/21。报告明确承认这是目的性抽样，且合并项不能证明 Function Calling 或 MCP 各自的精确覆盖率，因此这里只把它作为方向性旁证：[招聘需求与能力模型报告](https://todayforai.com/zh/guides/20260722-guide-agent-engineer-00-recruitment-requirements-report)。

官方接口也支持“工具调用已是基础能力、评测应同步建设”的判断：[OpenAI Function Calling](https://platform.openai.com/docs/guides/function-calling) 与 [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls) 都使用工具 schema 和应用侧执行流程；[OpenAI Evals](https://platform.openai.com/docs/guides/evals) 将评测视为构建可靠 LLM 应用的必要组成；[MCP 官方介绍](https://modelcontextprotocol.io/docs/getting-started/intro) 将其定位为连接 AI 应用与外部系统的开放标准，而不是 Agent 推理能力本身；[OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) 明确指出 RAG 不能消除注入风险，并建议最小权限、代码侧函数控制和攻击测试。

框架采用边界以官方定位为准：[LangChain 官方介绍](https://docs.langchain.com/oss/python/langchain/overview) 将其用于模型和工具等应用组件，[LangGraph 官方介绍](https://docs.langchain.com/oss/python/langgraph/overview) 面向长时、有状态和可控的 Agent 编排，[RAGAS 官方文档](https://docs.ragas.io/en/stable/) 提供 RAG/Agent 评测能力。因此本项目分别把它们放在适配层、单一多步骤工作流和辅助评测层，而不是让三个框架共同决定业务边界。

据此作出最终决策：Function Calling、领域 Eval 与 Prompt 回归保持 P0；LangChain 作为有边界的工程适配进入 Stage 11–12；RAGAS 从 Stage 11 开始作为辅助评测；LangGraph 在 Stage 13 只实现一个可解释的合规预检查图。安全保留与当前只读工具、权限和数据边界直接相关的最小闭环，不建设独立安全平台；MCP 不是“只有头部大厂需要”，但 JD 提及不等于作品必须优先实现，因此仍放在主线之后，只把一个已通过鉴权和评测的工具做 4–6 小时薄适配，不新增业务逻辑。

### 这个项目为什么有求职价值

这个项目具备让面试官记住的潜力，但亮点不是“用了 RAG/Agent”，而是以下能力能在同一条演示链路中被验证：

1. 同一个问题因为费用发生日期不同，能够命中不同的有效制度版本。
2. 每个结论能回到文件、版本、章节和真实页码，而不是只展示一段模型回答。
3. 没有足够证据时会拒答，并能展示对拒答和引用质量的独立评测。
4. 普通员工即使通过提示词诱导，也检索不到财务内部审核规则。
5. 能区分“制度问题走 RAG、个人报销状态走只读工具”，并用工具选择与参数正确率证明路由可靠。
6. 对“这张报销单可能为什么被退回”这类混合问题，先读取本人报销数据，再检索对应日期与场景的制度，输出风险、缺失材料和原文依据。

面试说服力来自代码、测试、评测报告和失败案例共同形成的证据链。只完成页面和模型调用不会眼前一亮；完成上述闭环后，即使不做 MCP 和多 Agent，也比堆叠技术名词更可信。

## 1. 产品定位

项目名称：**企业差旅报销制度合规助手**。

一句话价值：员工不必在多个制度、通知和旧版本之间反复查找，即可获得带有效版本和原文位置的报销办理指引；财务人员减少重复解释，同时内部审核 SOP 不会泄露给无权限用户。

### 目标用户

1. **普通员工**：出差前确认标准，差旅报销前确认流程、额度、发票和附件要求。
2. **财务审核人员**：快速定位规则依据，回答例外场景，访问内部审核 SOP。
3. **制度管理员**：上传新制度、标记版本和生效期、观察处理状态、下架旧版本。

### 只解决四类核心任务

1. **制度问答**：例如“2026 年 4 月去上海出差，住宿上限是多少？”
2. **办事指引**：例如“住宿费超标报销需要哪些附件，审批顺序是什么？”
3. **版本与权限判断**：例如“去年发生的费用应适用哪个版本？”以及“员工不能检索财务内部审核口径”。
4. **业务查询与合规预检查**：例如“我的报销单目前到哪一步了？”以及“这张报销单可能缺少什么材料？”状态题调用受身份约束的只读工具；预检查题组合本人报销数据与制度证据，但不替代财务作最终判断。

### 不做的事情

- 不连接真实 OA、ERP、财务系统，不自动发起或批准报销。
- 不接收 JPG/PNG 作为知识库文档，不做发票/截图 OCR、真伪核验、税务判断、图片问答或影像归档。
- PDF/DOCX 中允许存在图片，但当前版本不理解图片内容；系统必须显示图片内容未索引或扫描页需要 OCR，不能静默当作完整解析。
- 不根据一张发票自动完成全流程审核。
- 不允许模型生成或执行任意 SQL，也不允许模型自行声明用户身份。
- 不声称达到真实企业生产 SLA、并发量或成本节省。
- 不把模型生成内容当作最终财务意见；答案必须以制度证据为边界。
- 不为了简历关键词优先建设 MCP Server；只有核心工具、评测和主演示全部稳定且仍有时间时，才把一个现有只读工具增加为可选适配层。

## 2. 要解决的痛点与证明方式

### 痛点一：规定分散，找到原文慢

差旅标准、差旅报销办法、发票要求、审批权限表和补充通知可能分散在多个文件。关键词搜索只能返回文档，员工仍需自己判断章节和适用条件。

**系统方案**：混合检索后输出结论、步骤/材料和页码/章节引用，并允许打开来源上下文。

**证明方式**：选取 10 个代表性任务，分别记录人工目录/关键词查找与系统查找的“找到正确证据耗时”；报告中只写实测结果，不预设节省比例。

### 痛点二：旧版本被误用

同一制度存在修订版、补充通知和废止版本。只做向量相似度时，旧文档可能因为措辞更接近而排在前面。

**系统方案**：文档保存 `version`、`effective_from`、`effective_to`、`is_current` 和适用范围；先按问题日期和权限过滤，再做相关性排序。发生冲突时明确显示版本与日期，不静默混合。

**证明方式**：评测集中设置旧版/新版冲突题，单独统计“适用版本判断正确率”。

### 痛点三：重复咨询与材料遗漏

员工在提交差旅报销前不知道需要哪些附件、何时补审批、超标如何处理，导致财务反复解释或退回。

**系统方案**：使用固定回答结构输出“结论—适用条件—办理步骤—所需材料—例外/升级处理—依据”。第一版只覆盖国内差旅报销并提供制度指引，不伪装成自动审核。

**证明方式**：人工按标准答案检查材料项覆盖率与错误项；后续可选实现一个仅覆盖“国内差旅报销”的结构化自检表，但不扩大成完整审批系统。

### 痛点四：内部审核口径不应对所有员工可见

员工制度与财务内部稽核规则的可见范围不同。仅在前端隐藏入口不能阻止越权检索。

**系统方案**：权限条件进入候选检索 SQL；生成模型只能看到已过滤的 chunks。

**证明方式**：越权测试中检索结果、回答和引用均不得出现受限内容，泄漏数必须为 0。

### 产品价值的诚实边界

当前演示数据是虚构企业资料，因此可以证明系统具备解决上述问题的能力，但不能据此声称已为真实企业降低多少成本或退单率。若时间允许，邀请 3–5 名有报销经历的用户完成任务测试，记录完成率、耗时和最困惑环节；这比在简历中写未经验证的“效率提升 80%”更可信。

## 3. 最终可投递标准

### P0：没有这些就不是完整的垂直 RAG + 工具调用项目

1. PDF、DOCX、Markdown、TXT 的上传、校验、哈希去重和状态管理；JPG/PNG 返回明确的不支持提示。
2. 保留页码、标题层级、顺序、文档版本和生效日期的结构化切片。
3. PDF/DOCX 图片存在性与文本提取完整性检测；混合文档暴露警告，纯扫描无文字文档安全失败，任何未提取图片页都不能被引用。
4. PostgreSQL + pgvector 的向量检索，以及中文关键词检索。
5. dense、keyword、hybrid 的同一评测集对照。
6. 固定结构回答、来源引用、来源上下文和证据不足拒答。
7. 版本有效性过滤；旧版本不能仅因相似度高而成为当前规则依据。
8. 从 Stage 8 开始维护一套可复现的领域评测集，最终同时报告解析可靠性、检索、回答、工具路由、端到端结果和失败案例。
9. Prompt 模板进入版本控制，至少完成零样本基线、结构化 Prompt 和基于失败案例的少样本版本对照；以冻结测试集决定是否保留优化。

## 5. 领域数据与模型设计

### 演示企业与资料边界

使用虚构企业“星河科技”，资料只覆盖“国内出差申请—费用发生—报销提交—财务审核”链路，不扩展到招待费、采购付款等其他费用域：

```text
tests/fixtures/reimbursement_kb/
├─ 01_travel_policy/               # 差旅管理办法，含新旧版本
├─ 02_reimbursement_policy/        # 差旅报销管理办法
├─ 03_transport_hotel_meal/        # 交通、住宿、餐补标准
├─ 04_invoice_and_attachments/     # 发票与附件要求
├─ 05_approval_matrix/             # 审批权限和超标流程
├─ 06_supplementary_notices/       # 补充通知、例外规则
├─ 07_employee_faq/                # 员工公开 FAQ
└─ 08_finance_internal/            # 财务内部审核 SOP，受限
```

建议准备 12–18 篇高质量文档，而不是为了数量扩到多个无关部门。必须至少包含：

- 一份旧制度和一份替代它的新制度。
- 一份晚于主制度发布的补充通知。
- 一份只有财务角色可见的内部 SOP。
- 表格、分级标题、跨页内容和空白页等解析边界。
- 一份带装饰图片但正文可提取的 PDF、一份“部分文本页 + 部分扫描页”的混合 PDF，以及一份含嵌入图片的 DOCX，用于验证系统不会静默遗漏视觉内容。
- 有意留出知识库未覆盖的问题，用于拒答评测。

### Document 需要补充的领域字段

通用存储字段之外，建议补充：

| 字段 | 用途 |
| --- | --- |
| `sha256` | 文件去重和幂等处理 |
| `document_type` | policy / notice / faq / internal_sop |
| `version` | 可展示的制度版本号 |
| `effective_from` | 开始生效日期 |
| `effective_to` | 失效日期，可为空 |
| `is_current` | 管理端快速识别，不替代日期判断 |
| `access_scope` | employee / finance / admin |
| `supersedes_document_id` | 表示替代关系，可为空 |
| `embedded_image_count` | 解析器检测到的嵌入图片数量；只表示存在，不表示已理解 |
| `image_only_page_count` | PDF 中“有图片且可提取文字低于阈值”的页数；DOCX 无稳定页码时可为空 |
| `text_extraction_status` | complete / partial / unavailable，与业务处理状态分离 |
| `needs_ocr` | 是否存在无法通过原生文本解析覆盖的扫描页 |
| `parse_warnings` | 结构化警告，例如图片未索引、扫描页、远程图片未获取 |

不要尝试由大模型自动猜测所有元数据。第一版由上传者填写，系统校验日期区间；后续可以做“模型提取、人工确认”。当用户没有提供费用发生日期且不同版本会导致不同答案时，系统必须追问；只有不存在版本歧义时，才可按当前有效制度回答并明确这一假设。

### Chunk 必须保留的字段

- `document_id`、`chunk_index`、`content`、`content_hash`。
- `page_start`、`page_end`；DOCX 没有稳定页码时使用章节路径，不制造假页码。
- `section_path`，例如“第四章/第二节/住宿费”。
- `extraction_method`，本周期为 `native_text`；若 Stage 16 做 OCR，新增 `ocr`，最终引用仍必须保留原页码。
- `token_count` 或可重复计算的长度指标。
- 冗余的检索过滤字段：知识库、访问范围、有效日期，或者通过可靠 join 过滤。
- embedding 和中文关键词检索字段。

### 图片与扫描页处理契约

本项目的“支持带图片文档”含义是：允许 PDF/DOCX 中存在图片，同时明确哪些内容已索引、哪些没有；它不等于理解图片，也不等于支持多模态问答。

1. **原生文字 PDF**：逐页提取文字并统计嵌入图片。正文可可靠提取时正常切片；Logo、盖章等图片不单独进入向量库。
2. **纯扫描 PDF**：当所有页面都没有可用文字且检测到页面图片时，设置 `needs_ocr=true`、`text_extraction_status=unavailable`，业务状态进入 `failed`，返回“当前版本需要 OCR”的安全错误，不生成空 chunks。
3. **混合 PDF**：可提取页正常生成 chunks；疑似扫描页不生成伪文本，文档业务状态可以是 `ready`，但 `text_extraction_status=partial`、`needs_ocr=true`，API、管理页面和回答上下文必须展示警告。
4. **含图 DOCX**：继续提取段落与标题，统计嵌入图片并记录“图片内容未索引”；由于 DOCX 没有稳定页码，不虚构图片所在页。
5. **Markdown 图片与外部地址**：可以保留 alt text 作为原文的一部分，但解析器不主动下载本地或远程图片，避免 SSRF、路径访问和不可复现依赖；同时记录图片未获取警告。
6. **独立 JPG/PNG、发票照片和截图**：上传校验直接拒绝并说明产品边界，不把它们伪装成制度文档。

图片页判定使用可配置、可测试的启发式规则，例如“页面存在图片且规范化文字少于阈值”，不宣称能判断图片是否包含重要业务信息。`pending / processing / ready / failed` 四种业务状态保持不变，提取完整性由上述独立字段表达。

回答层只能引用真实生成的文字 chunks。若引用文档为 `partial`，系统可以回答被现有文字直接支持的正向事实，但必须附带“部分页面未解析”提示；对“制度中没有要求某材料”这类依赖全文完整性的否定结论，应拒绝确认并建议补充可搜索版本或执行 OCR。

### 固定回答契约

有依据时返回：

```text
结论
适用条件与制度版本
办理步骤 / 所需材料
例外情况或需人工确认项
来源（文件名、版本、章节、页码）
```

无足够依据时返回：

```text
现有知识库无法确认该问题。
已检索的相关制度范围：...
建议咨询的角色或需要补充的信息：...
```

禁止只因为检索到了相似文本就回答；拒答由“证据覆盖规则 + 提示词约束 + 测试”共同实现，不把单一相似度阈值包装成绝对可靠。

### 技术决策

- API：FastAPI + Pydantic + SQLAlchemy Async + Alembic。
- 数据库：PostgreSQL + pgvector；所有结构变更走迁移。
- 解析：P0 使用 pypdf、python-docx、Markdown/TXT 原生文本解析，并逐文档/逐页记录图片存在性和文字提取覆盖；pypdf 不是 OCR 引擎，扫描页不得被误判为已解析，参见 [pypdf 文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)。
- OCR/多模态：P0 不调用视觉模型、不做图片 embedding，也不接收独立 JPG/PNG。Stage 16 只有在代表性制度确实需要时，才在 [OCRmyPDF](https://ocrmypdf.readthedocs.io/en/latest/introduction.html) 或 [PaddleOCR](https://www.paddleocr.ai/latest/en/index.html) 中选择一个做扫描 PDF 试点；OCR 输出必须重新经过现有切片、引用和评测链路。
- embedding：Provider 接口隔离供应商，开发默认使用小型本地中文模型。
- 生成模型：OpenAI-compatible Provider；测试中使用 fake provider，避免自动化测试依赖网络和费用。
- 关键词检索：应用侧中文分词后写入 PostgreSQL 可检索字段；记录分词方案，保证评测可复现。
- 融合：先用 RRF 或简单加权；只有离线数据证明 reranker 有提升才保留。
- 后台任务：先把解析/切片/向量化写成与执行器无关的幂等服务，核心检索基线完成后再接 Celery。
- 前端：只承担操作和证据展示，不在前端实现权限判断或核心业务规则。
- LangChain：Stage 11–12 有边界地使用。它负责版本化 Prompt 的装配、模型 Provider 适配、结构化输出和工具绑定；Hybrid Retriever、Policy Scope Resolver、鉴权、资源归属和领域规则保持独立 Python 服务，测试不得必须联网或依赖框架内部对象。
- Prompt 策略：先建立零样本基线，再测试结构化指令和由调优集失败案例提炼的 2–4 个少样本示例；同一模型、温度、上下文和冻结测试集下比较质量、延迟与成本。不得把只在少数演示题上有效的手工 Prompt 写成普遍提升。
- 推理展示：可以比较“直接回答”和“结构化任务分解/证据清单”，但不要求、保存或向用户展示模型原始思维链。财务合规场景只输出业务事实、制度依据、规则命中、缺失材料和简短结论理由。
- 工具调用：用 Pydantic 定义严格参数 schema，通过 LangChain 的模型/工具适配层或 Provider 原生结构化接口在 `search_policy`、`query_reimbursement_status`、`get_reimbursement_detail` 等白名单能力之间选择；服务端执行前必须重新鉴权。领域工具自身不能依赖模型生成的身份或任意 SQL。
- LangGraph：只在 Stage 13 编排合规预检查，节点调用现有领域服务；图中明确正常、无权限、工具失败、证据不足路径。制度问答和单次状态查询保持简单调用链，不为了展示框架而图化。
- RAGAS：从 Stage 11 接入辅助评测，记录版本、模型、Prompt 和运行成本，并与人工抽样对齐。它不替代 Recall@K、MRR、版本正确率、引用正确率、拒答、工具路由和越权硬门槛。
- 能力路由：制度题只使用版本感知检索；进度题调用状态工具；合规预检查先读取本人报销明细，再检索费用发生日期对应的制度。业务系统事实与模型建议必须分栏展示，模型不能伪造工具结果。
- 身份边界：状态与明细工具的用户身份只来自 JWT 请求上下文，不让模型传入 `user_id`，不暴露任意 SQL，也不提供批准、驳回或修改报销单的写工具。
- MCP：不进入核心路线。Stage 16 只有在核心工具稳定、评测与主演示完成后，才允许将一个现有只读服务增加为薄适配层；MCP 不新增业务权限，也不能绕过原服务的鉴权、审计和参数校验。

### 安全信任边界

简单匹配“忽略之前指令”等关键词不能被称为 Prompt Injection 防护：它既可绕过，也会误伤正常问题。系统采用以下可测试边界：

1. **输入层**：限制长度、结构和工具参数；高风险模式用于告警/审计，不作为唯一防线。
2. **检索层**：知识库、角色、文档访问范围和有效日期进入数据库查询条件；未授权 chunk 在调用模型前就被排除。
3. **上下文层**：把上传文档视为不可信数据，文档中的命令、角色声明和工具调用要求不得改变系统指令；Markdown/文档中的图片路径和远程 URL 不主动读取，嵌入图片也不自动发送给外部视觉模型。
4. **工具层**：工具白名单、最小只读权限、严格 schema、超时和审计；执行器使用服务端身份上下文再次校验资源归属。
5. **输出层**：只允许引用实际提供给模型且用户有权访问的证据；过滤内部字段和安全错误详情。
6. **评测层**：覆盖直接提示注入、恶意文档间接注入、跨用户报销单查询、越权引用和工具参数篡改。

这些措施不能宣称“完全防住 Prompt Injection”；项目应表述为建立纵深防御和可回归的攻击测试，并公开仍存在的边界。

## 7. 重排后的秋招路线

路线原则：**先在一个垂直场景中跑通并量化 RAG，解析阶段就识别未提取的图片/扫描内容并建立评测；回答阶段同步完成 Prompt 对照、LangChain 边界集成和 RAGAS 辅助评测；RAG beta 后立即加入 Function Calling，再用 LangGraph 编排合规预检查，最后补异步和界面。** Function Calling 不能早于可靠检索，否则只是数据库查询演示；LangGraph 不能早于稳定的节点服务和失败语义，否则只是把不稳定代码画成图；完整多模态不能早于文本主链路，否则会显著扩大数据、成本和评测范围。

## 8. 评测设计与验收指标

### 问题集组成

评测与功能同步建设，不等项目完成后补题：Stage 8 建立 20 题 v0 和统一标注契约，Stage 9–10 扩到 40+ 题，Stage 12 加入工具路由题，最终形成 60–80 题。建议以 70 题为计划基线：

| 类型 | 建议数量 | 目的 |
| --- | ---: | --- |
| 单段事实题 | 12 | 检查基础召回与精确引用 |
| 多条件题 | 8 | 日期、人员级别、城市/费用类型等条件组合 |
| 跨章节/跨文档题 | 6 | 主制度、附件、补充通知之间的关联 |
| 新旧版本冲突题 | 8 | 验证有效期过滤和冲突展示 |
| 无答案/信息不足题 | 6 | 验证拒答，不诱导编造 |
| 工具路由与状态题 | 10 | 验证工具选择、参数提取、异常处理和不必要调用 |
| 混合合规预检查题 | 8 | 验证报销数据、费用日期和制度证据的组合推理 |
| 越权与攻击题 | 12 | 验证受限资料、跨用户单据、提示注入和工具参数篡改不突破边界 |

每题至少记录：

- 问题、用户角色、问题发生日期和必要上下文。
- 标准文档、版本、相关 chunk IDs 和可接受答案要点。
- 检索策略、Top K、命中排名、最终引用。
- 是否应拒答、人工评分和失败原因标签。
- 数据集版本、Prompt 版本、模型/Provider 标识、温度和主要推理配置。
- 预期能力路由、允许调用的工具、标准参数和模拟工具结果。
- 预期资源归属结果、是否应禁止执行，以及业务事实/制度依据/系统建议的边界。

评测集建立后分成调优集与冻结测试集：40–50 题用于调 chunk、权重、提示词和路由，至少 20 题在最终报告前保持冻结。最终简历数字以冻结集为准，避免反复针对同一批问题调参造成虚高。检索命中的计算规则也要固定：Top K 中出现任一标注相关 chunk 视为该题召回，存在多个正确来源时全部保留在标注中。

### 解析完整性测试

图片处理不混入 70 题问答准确率，而是建立独立、确定性的 parser fixtures 与测试：

| Fixture | 预期结果 |
| --- | --- |
| 带 Logo/盖章、正文可提取的 PDF | 正文正常切片；记录图片数量；不因装饰图误标整份文档不可用 |
| 每页只有扫描图片的 PDF | `failed + unavailable + needs_ocr`；无 chunks；返回安全错误 |
| 部分原生文字、部分扫描页的 PDF | `ready + partial + needs_ocr`；只为可提取页建 chunks；API/页面显示页码警告 |
| 含段落文字和嵌入图片的 DOCX | 文字正常切片；图片计数与未索引警告存在；不制造图片页码 |
| 包含本地路径或远程 URL 的 Markdown 图片 | 不发生文件/网络读取；保留允许的 alt text；记录警告 |
| 独立 JPG/PNG 或伪装扩展名 | 上传拒绝；不落盘或失败后完成清理 |

上述已知 fixture 的扫描/图片边界必须全部命中，未提取页不得产生引用；同时记录装饰图误报和阈值配置。该结果只能表述为“固定边界测试全部通过”，不能外推为任意扫描文档识别率 100%。

### 检索指标

- Recall@5 目标 ≥ 0.80。
- MRR 目标 ≥ 0.60。
- 版本适用判断正确率目标 ≥ 0.90。
- 分别报告 dense、keyword、hybrid；不能只展示最好的一次运行。
- 保留配置、模型标识、chunk 参数、数据集版本和随机种子，保证结果可复现。

### 回答指标

- 引用正确率目标 ≥ 0.90：引用内容确实支持对应结论。
- 答案要点覆盖率：依据人工 rubric 统计，不能只用主观“看起来不错”。
- 无答案题分别报告拒答 precision、recall，避免通过“全部拒答”刷准确率。
- 版本冲突题必须在答案中出现适用日期/版本。
- 引用了 `text_extraction_status=partial` 的文档时必须显示覆盖警告；依赖全文完整性的否定结论不得仅凭部分提取内容生成。
- 自动 LLM judge 只能作辅助；最终报告抽样人工复核。

### Prompt 策略与实验边界

Prompt 优化必须像代码一样可版本化、可回滚、可回归。Stage 11 至少保留三组可比较结果：

1. **V0 零样本基线**：只包含必要角色、任务、上下文和输出契约，不放示例。
2. **V1 结构化 Prompt**：明确系统指令、不可信检索上下文边界、引用/拒答规则和结构化字段。
3. **V2 少样本版本**：只从调优集的真实失败类型中选择 2–4 个代表性示例，不得引用冻结测试题，也不为了个别题不断堆示例。

比较时固定模型、温度、检索结果、数据集版本和输出 schema，同时报告答案质量、引用/拒答指标、平均延迟、token/费用。只有 V2 在冻结集上有稳定收益且成本可接受时才进入最终默认版本；否则保留更简单的 V1。

“熟悉思维链”通过受控实验和设计说明体现，而不是向用户暴露模型私有推理。可比较直接回答与结构化任务分解，但生产输出只保留可审计的事实、证据、规则命中、缺失材料和简短理由；不保存或展示原始 Chain-of-Thought。

### RAGAS 辅助评测边界

Stage 11 起接入 RAGAS，对上下文检索质量、回答忠实度和回答相关性提供辅助视角；Stage 15 在同一冻结集上同时展示 RAGAS、项目自定义指标和人工抽样结果。每次运行保存 RAGAS 版本、评判模型、Prompt 版本、数据集版本、失败日志、token/费用与耗时。

RAGAS 不能替代以下领域判断：制度版本是否适用、引用是否精确支持具体结论、拒答是否正确、工具选择与参数是否正确、资源归属是否越权、合规预检查是否混淆事实与建议。若 RAGAS 与人工标注明显冲突，先归因并公开差异，不为了得到更高总分修改人工标准答案。

### Function Calling 与端到端指标

- 能力/工具选择准确率目标 ≥ 0.90；分别统计制度题、状态题和混合预检查题，不能只报总体平均。
- 工具参数正确率目标 ≥ 0.95；`claim_id` 等关键参数按标准化后的 exact match 统计。
- 普通制度题误调用报销数据库的比例目标 ≤ 0.05。
- 工具执行成功率与任务成功率分开统计：工具成功不代表最终回答正确。
- 合规预检查端到端通过率目标 ≥ 0.80，人工 rubric 至少检查业务事实、适用版本、引用支持、风险说明和不越权五项。
- 单号不存在、超时和服务异常必须进入安全失败路径，不得编造状态或把内部异常详情返回用户。
- LangChain 层必须有 fake model/tool 测试；替换或绕过 LangChain 适配层时，领域工具、鉴权和检索测试仍可独立运行。
- LangGraph 至少覆盖正常完成、无权限、工具失败、证据不足四条路径；节点重试不得造成重复写入或绕过鉴权，并记录最终停止原因。

### 安全与可靠性硬门槛

本项目不建设大厂级安全平台，但下面这些是数据库工具和企业资料场景的最小安全闭环，不能因项目规模小而删除：

- 越权检索泄漏数必须为 0；这是门槛，不取平均分。
- 直接提示注入不能改变当前用户角色或扩大检索范围；包含恶意指令的文档不能触发工具或改变回答规则。
- 跨用户查询、模型伪造身份、非白名单工具调用和写操作请求必须全部被拒绝并留下审计记录。
- 删除文档后原文件、chunks、向量均被清理。
- 同一索引任务重复执行不产生重复数据。
- 解析失败后状态为 `failed`，保存对用户安全的错误摘要并允许重试。
- 扫描页、嵌入图片和 Markdown 图片地址不得被静默当作已索引内容；解析器不得主动访问文档提供的本地路径或远程图片 URL。

安全评测不能只准备两条“忽略之前指令”用例。至少包括同义改写、角色冒充、编码/分隔符变体、恶意内容藏在检索文档中、要求泄漏系统提示词、跨用户资源 ID 和工具参数篡改。项目只承诺这些测试覆盖的边界，不声称解决了所有 Prompt Injection。

### Function Calling 与垂直闭环验收

- 制度题错误调用工具的比例。
- 进度题的工具选择正确率和 `claim_id` 参数提取正确率。
- 单号不存在、工具超时和服务异常时是否给出安全、可理解的结果。
- 查询他人单据、伪造用户身份和恶意参数的拒绝率必须为 100%。
- 混合问题能否清楚区分“业务系统返回的当前状态”和“制度文档提供的规则依据”。
- 合规预检查是否使用费用发生日期对应的制度，是否把模型建议误表述为财务审批结论。
- LangGraph 是否真正承载了多步状态与条件分支；若只是顺序调用，不得把使用框架本身当作 Agent 亮点。

### 产品任务实验

用 10 个固定任务对比人工查文档与系统查证据，记录：完成与否、找到正确来源的耗时、版本判断是否正确、主观信心。由于样本小且资料虚构，只把结果描述为“演示环境任务实验”，不外推真实企业 ROI。

## 9. 演示主流程

5 分钟演示只讲一个完整故事，不浏览功能菜单。上传、解析、索引和文档管理在演示前准备好，现场只用十几秒展示一份混合 PDF 的“部分扫描页未索引”警告，并证明可用来源仍可追溯：

1. 员工询问一个带日期和条件的住宿标准问题，系统走版本感知 RAG，返回结构化答案、新版依据和真实页码/章节。
2. 追问旧日期，系统切换到当时有效版本；再问一个知识库没有覆盖的问题，系统拒答而不是编造。
3. 员工问“我的报销单 `#12345` 到哪了”，系统调用受身份约束的只读状态工具，并展示精简的工具名、参数和结果状态。
4. 员工继续问“这张单据可能为什么被退回”，LangGraph 合规预检查依次完成资源归属校验、本人报销明细读取、费用日期对应制度检索和证据检查，分别展示业务事实、制度依据、风险与缺失材料，并声明这不是最终审批结论；页面只显示可审计节点状态，不显示原始思维链。
5. 尝试查询另一用户的单号，服务端资源归属校验拒绝执行；模型无法通过提示词伪造身份。
6. 最后展示 dense/keyword/hybrid、Prompt V0/V1/V2、RAGAS 辅助结果、引用/拒答、工具路由和端到端指标，以及一个仍未解决的失败案例；只展示一页关键对照，不在主演示中浏览全部实验日志。

这个流程同时覆盖产品价值、解析完整性、版本意识、可信引用、Prompt 优化证据、LangChain 有限集成、Function Calling、LangGraph 条件工作流、RAGAS 辅助评测、垂直业务联动、安全边界和工程可测性，无需加入多 Agent 或完整多模态才成立。OCR/MCP 即使实现也只放在主演示之后作为短增强说明，不能挤占业务闭环。

## 10. 时间风险与降级规则

任何延误都先保护以下七项：

1. 版本正确的来源引用。
2. dense/keyword/hybrid 对照。
3. 有标签的离线评测与失败案例。
4. 制度/状态/合规预检查三类任务的工具路由闭环。
5. 权限过滤、报销单资源归属和只读工具不泄漏、不越权。
6. Prompt 版本与冻结集回归，保证优化结论可复现。
7. 图片/扫描页提取不完整必须可见，未提取内容不能被静默引用或用于否定结论。

按以下顺序降级：

1. 不做完整多模态、发票/截图 OCR、图片向量检索、MinIO/S3 和多 Agent；P0 图片/扫描页检测与警告不能删除。
2. 不做 Stage 16 OCR 试点或 MCP Server；它们都不能替代可靠文本解析、Function Calling、工具鉴权或业务闭环。
3. 不做 reranker 和流式回答。
4. RAGAS 只保留一套冻结集运行与人工校准，不扩展多评判模型或复杂可观测平台；自定义领域指标不能删除。
5. Redis + Celery 降级为同步幂等索引服务，不做复杂队列编排、定时任务或监控平台。
6. 合规预检查先只覆盖住宿费与附件缺失两个高频规则，不扩展到完整财务审核规则库；但保留状态工具和能力路由。
7. LangGraph 只保留正常、无权限、工具失败、证据不足四条路径；若框架问题影响主链路，退回已有显式状态机，先保证相同业务验收和测试，不删除工作流设计说明。
8. 权限只做最小两类可见范围，不扩展复杂组织树和 RBAC 管理界面。
9. 前端只做主流程，不投入动画、主题和复杂组件。
10. 不做结构化报销自检表。

若 **2026-08-16** 仍未产出可复现的 dense baseline，暂停文档管理增强，优先跑通 parse → chunk → embed → retrieve。  
若 **2026-08-30** 仍未完成混合检索评测和引用回答，Celery、前端和新增功能全部后移。  
若 **2026-09-06** 工具路由仍不稳定，不扩展 LangChain 抽象或增加更多工具，先固定 `search_policy` 与 `query_reimbursement_status` 两条路径及其评测；领域工具继续保持框架无关。  
若 **2026-09-13** 垂直闭环仍不稳定，将合规预检查缩到一个住宿超标场景，并允许 LangGraph 退回显式状态机；缩减前端，但不牺牲工具鉴权、测试、Prompt 回归和评测报告。

Stage 16 增强决策以 Stage 8/15 数据为准：只要核心制度的关键页面因扫描而无法进入评测，OCR 试点优先；若所有代表性制度均有可靠原生文字，则不为“多模态”标签做 OCR，保留 MCP 或直接用于修复和面试复盘。

## 11. 协作、学习与 Git 规则

用户是大三学生，目标是能够解释和修改系统，而不是只把代码跑起来。每阶段维持以下节奏：

1. 先说明本阶段解决的业务问题、调用链和不做什么。
2. 一次只实现当前阶段的最小闭环。
3. 按文件说明职责，重点解释设计原因和失败路径。
4. 用户亲自运行单元测试、真实依赖和至少一个反例。
5. 用户回答理解题并修改一个小功能或测试。
6. Ruff、pytest、迁移和真实接口检查通过。
7. 更新阶段记录和 README，用户创建独立 Git commit。

工程完成与学习完成分开记录。测试通过只代表代码达到当前验收条件，不代表用户已经能在面试中解释。

### 从核心到框架的学习与代码阅读顺序

不要先从 LangChain/LangGraph 教程或前端入口切入。每个阶段按“契约 → 纯业务服务 → 框架适配 → API → 测试/评测”阅读，具体文件名以阶段实现时的学习文档为准：

1. **数据与输出契约**：先看 Pydantic schema、数据库模型和 `EvalCase`，弄清输入、输出、状态与错误语义。
2. **解析和检索核心**：看 parser、图片/扫描页检测、提取完整性、chunker、embedding、dense/keyword/hybrid 与版本/权限过滤；先能独立解释什么内容真正进入了索引，再解释 RAG，不依赖 LangChain 名词。
3. **Answer Service 与 Prompt**：先看 V0/V1/V2 模板、上下文拼装、引用检查和拒答规则，再看模型调用。
4. **LangChain 适配层**：只追踪 Prompt 如何传入模型、结构化输出如何解析、工具 schema 如何绑定；同时确认核心服务可以被 fake provider 直接测试。
5. **自定义评测 → RAGAS**：先理解 Recall@K、MRR、版本/引用/拒答的标签怎么算，再看 RAGAS 如何增加辅助评分，避免只会调用评测库却解释不了指标。
6. **工具与权限**：依次看 JWT 请求上下文、资源归属、只读 repository、工具 schema、执行网关和审计，确认模型不能决定身份。
7. **LangGraph 合规预检查**：按 `State → Nodes → Conditional Edges → Compile/Invoke → Tests` 阅读；每个节点先回到它调用的普通领域服务，再看图如何组织流程。
8. **API、前端与演示**：最后看路由和页面如何组合以上能力，不从 UI 倒推核心设计。

学习验收不是背诵 API：需要能画出一次请求的调用链，解释为什么某段代码属于框架适配而不是业务核心，并能在不看答案的情况下修改一个 Prompt 实验、一个工具失败分支或一个评测用例。

每阶段提交前执行：

```powershell
cd D:\xuexi\projects\agent_project\backend
..\.venv\Scripts\python.exe -m ruff check app tests
..\.venv\Scripts\python.exe -m pytest
..\.venv\Scripts\python.exe -m alembic current
cd ..
git status
```

每个简历能力都必须能指向至少一种证据：代码、测试、迁移、评测结果、日志或演示录像。不要为整理 Git 历史重写已经共享的提交，也不要把本地真实 `.env` 和上传数据提交进仓库。

## 12. 下一次会话入口：Stage 8

Stage 7 已完成并通过真实数据库/API 验收。下一次进入解析与结构化切片，不重复摄取层，也不先接 embedding 或大模型。

### Stage 8A：先冻结解析输出契约

1. 阅读 Stage 7 的 StorageService、格式校验、Document 状态与 45 项测试。
2. 定义 `ParsedDocument` / `ParsedSection`：正文、页码、标题层级、顺序、嵌入图片数量、疑似扫描页、文字提取状态和结构化警告。
3. 明确 PDF 有真实页码；DOCX 没有稳定页码时只记录章节路径，不能制造假页码。
4. 先定义空文档、加密/损坏文档、纯扫描 PDF、混合 PDF、部分页面失败和重复解析的状态语义；业务状态仍使用 `pending / processing / ready / failed`，提取完整性单独表达。

### Stage 8B：Parser Registry 与真实解析器

1. 建立 Parser 协议与按文档格式分派的注册表。
2. 使用 pypdf 提取逐页文本并统计图片/低文字页，使用 python-docx 保留标题层级并统计嵌入图片；MD/TXT 复用纯文本解析器，Markdown 图片不得触发本地或远程读取。
3. 解析器只返回结构化中间结果，不直接操作数据库。
4. 为正常、空白、损坏、加密、表格、跨页、装饰图 PDF、纯扫描 PDF、混合 PDF、含图 DOCX 和 Markdown 图片建立 fixture 与测试。

### Stage 8C：领域元数据与 chunks

1. 为 Document 增加制度类型、版本、生效/失效日期、访问范围、替代关系，以及 `embedded_image_count`、`image_only_page_count`、`text_extraction_status`、`needs_ocr`、`parse_warnings`。
2. 建立 `document_chunks` 表，保存文档、顺序、正文、页码范围、章节路径、长度指标和内容哈希。
3. 先实现确定性的标题感知切片，记录参数；只为可提取文字创建 chunks，未提取图片页不得生成空 chunk 或伪造内容；不在本阶段做向量化。
4. 重复处理必须先替换或复用原 chunks，不产生重复数据。

### Stage 8D：同步建立评测集 v0

1. 先定义可版本化的 `EvalCase` 契约，至少记录问题、角色、费用发生日期、标准文档/版本、相关章节、可接受答案要点、是否应拒答和失败标签；为运行结果预留数据集版本、Prompt 版本、模型/Provider、温度和成本/延迟字段。
2. 从演示制度中人工编写首批 20 题，覆盖事实、多条件、跨文档、版本冲突、无答案和越权；不能只用模型自动生成后直接当标准答案。
3. 为未来工具题预留 `expected_route`、`expected_tool`、`expected_arguments` 和 `execution_allowed` 字段，本阶段允许为空。
4. 本阶段只验证数据契约、标注可复核以及解析/chunk 输出能否支持标注，同时运行独立的图片/扫描边界测试；不提前伪造 Recall、OCR 准确率或回答准确率。

### Stage 8 完成条件

- 四种格式都能产生确定、可重复的解析结果。
- PDF chunk 能追溯真实页码，DOCX chunk 能追溯章节路径。
- 原生文字 PDF、纯扫描 PDF、混合 PDF、含图 DOCX、Markdown 图片和独立 JPG/PNG 的预期边界全部通过自动化测试。
- 纯扫描/空文档和解析失败进入 `failed` 并保存安全错误摘要；混合 PDF 可进入 `ready`，但必须标记 `partial + needs_ocr` 并列出未提取页。
- 未提取图片页不生成 chunks、不进入 embedding、不产生引用；解析器不访问 Markdown 图片指向的本地或远程资源。
- 新旧制度版本与访问范围可以录入和查询。
- 20 题评测集 v0 能随代码版本化，每题能指向预期文档、版本和章节。
- 评测运行契约能区分数据集、检索配置、Prompt、模型和框架版本，为 Stage 11 的 LangChain/Prompt/RAGAS 对照留出稳定接口。
- 用户能解释解析、切片和持久化为什么分层，以及 chunk 边界怎样影响后续召回。
